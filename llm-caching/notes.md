# LLM 上下文压缩工具全景调研与缓存影响分析

> 调研日期：2026-06-25
> 核心问题：在国内 100 倍缓存差价场景下，使用上下文压缩工具到底是省钱还是亏钱？
> 关联：[[headroom]]

---

## 一、调研的工具清单

| 工具 | 类型 | 语言 | Stars | 核心思路 |
|------|------|------|-------|---------|
| **RTK** | CLI 输出过滤 | Rust | 高 | 只压缩命令输出，不动请求 |
| **lean-ctx** | 上下文工程层 | Rust | 1.8k+ | 确定性压缩，字节级缓存安全 |
| **Headroom** | 压缩库+代理 | Python+Rust | 高 | ML+规则混合压缩 |
| **LLMLingua** | 研究工具 | Python | 高 | 用小模型删除非必要 token |
| **The Token Company** | 商业云服务 | 云 | — | 训练模型做 keep/delete 分类 |

## 二、逐个工具分析

### 2.1 RTK（Rust Token Killer）

**它做什么**：包装 CLI 命令（`git status`、`ls`、`grep`、`pytest` 等），在输出到达 LLM 之前过滤和压缩。

**它不做什么**：不碰 API 请求、不碰对话历史、不碰系统提示词。

```
Claude  --git status-->  RTK  -->  shell  -->  git
  ^                       |
  |   ~200 tokens         | filter (去掉噪音)
  +--- (过滤后的输出) -----+
```

**压缩率**：60-90%（仅限命令输出）

**对缓存的影响**：✅ **零影响**
- RTK 只过滤命令的 stdout，然后作为 tool_result 返回
- tool_result 本来就是每轮不同的新内容，不在缓存前缀中
- 系统提示词、工具定义、对话历史完全不变
- Provider 的 KV 缓存完全不受影响

**适用场景**：编程 Agent 日常使用（Cursor、Claude Code、Codex 等）

**结论**：最安全的选择。只压缩本来就不会被缓存的内容。

---

### 2.2 lean-ctx

**它做什么**：一个完整的上下文工程层，包含：
- 10 种文件读取模式（`map`、`signatures`、`diff` 等）
- 95+ 种 shell 输出压缩模式
- 可选的请求代理（proxy），压缩整个请求
- 77 个 MCP 工具
- 会话记忆、代码图谱、语义搜索

**关键特性：确定性 + 缓存安全**

lean-ctx 明确将 **"prompt-cache-safe"** 作为核心设计原则：

> `/v1/compress` is **deterministic by contract**: the same `(messages, model)` produces byte-identical output, so Anthropic (90%) and OpenAI (50%) prompt-cache discounts survive compression.

具体做法：
1. **字节级确定性**：相同输入 → 相同输出（byte-identical），由 CI 测试保证（issue #498）
2. **冻结边界**：只在冻结的、缓存感知的边界处裁剪历史
3. **不动 cache_control 标记的内容**：客户端标记为缓存的内容永远不会被修改
4. **`cache_preservation_ratio` 参数**：可配置保留多少缓存前缀

**两种工作模式**：

| 模式 | 做什么 | 对缓存的影响 |
|------|--------|------------|
| **MCP 工具模式** | 只压缩 lean-ctx 自己的工具输出（文件读取、shell 命令） | ✅ 零影响（工具输出本来就不在缓存前缀中） |
| **Proxy 代理模式** | 压缩整个请求（系统提示词、历史、工具结果） | ⚠️ 有影响，但通过确定性压缩保证缓存安全 |

**Proxy 模式的缓存安全机制**：
- 压缩是确定性的 → 第 N 轮和第 N+1 轮的压缩结果一致 → 前缀稳定
- 不动 `cache_control` 标记的内容 → Anthropic 缓存断点不受影响
- `cache_preservation_ratio` → 可以配置保留多少未压缩的前缀

**lean-ctx 自己的成本分析**（来自官方文档）：

| 因素 | 净收益 | 可能亏本 |
|------|--------|---------|
| 上下文生命周期 | 长生命周期（同一个 agent loop） | 相位隔离（每阶段新进程） |
| Provider 定价 | 有 prompt cache 的 Provider | 无缓存 / 按请求计费 |

| 覆盖范围 | 生命周期 | 定价 | 结论 |
|---------|---------|------|------|
| proxy/引擎 | 长生命周期 | 有缓存 | **明确收益** |
| proxy/引擎 | 长生命周期 | 无缓存 | **收益**（压缩收益 > 前缀开销） |
| 仅工具 | 长生命周期 | 有缓存 | **小幅收益** |
| 仅工具 | 相位隔离 | 无缓存 | **持平** |

**结论**：最注重缓存安全的工具。如果你在意缓存命中率，lean-ctx 是最谨慎的选择。

---

### 2.3 Headroom

**它做什么**：压缩库 + 代理 + MCP 服务器，支持 ML 压缩（Kompress-base）。

**对缓存的影响**：

Headroom 的 CacheAligner 是 **纯检测器**（当前版本），不会修改消息内容。但 Headroom 的压缩器（SmartCrusher、CodeCompressor 等）会改变内容。

**关键问题**：Headroom 没有明确的 "deterministic" 或 "prompt-cache-safe" 保证。

从 lean-ctx 对 Headroom 的对比文档中：

> **lean-ctx**: Determinism: Byte-stable output, prompt-cache safe (#498)
> **Headroom**: Not a stated contract

这意味着：
- Headroom 的压缩结果可能不是确定性的（尤其是 ML 模型部分）
- 如果压缩结果不确定，前缀就不稳定，缓存就无法命中
- 没有明确的缓存安全保证

**Headroom 的优势**：
- ML 压缩（Kompress-base）对自由文本的压缩率更高
- 更多框架集成（Agno、Strands、LangChain 等）
- 纯 Python/Node，无需单独的 daemon

**Headroom 的风险**（在国内 100 倍差价场景下）：
- 没有确定性保证 → 压缩结果可能每轮不同 → 前缀不稳定 → 缓存失效
- ML 模型输出不确定 → 即使规则部分确定，ML 部分也可能破坏缓存

**结论**：如果你的 Provider 有显著的缓存价格差，Headroom 的风险较大。

---

### 2.4 LLMLingua（微软）

**它做什么**：用小模型（GPT-2 small、LLaMA-7B、BERT-level）识别并删除 prompt 中的非必要 token。

**核心论文**：
- LLMLingua (EMNLP 2023)：20x 压缩，最小性能损失
- LongLLMLingua (ACL 2024)：解决 "lost in the middle" 问题
- LLMLingua-2 (ACL 2024 Findings)：3-6x 速度提升

**对缓存的影响**：❌ **不友好**
- ML 模型的输出不确定（不同运行可能有微小差异）
- 没有缓存安全设计
- 主要是研究工具，不是生产级 Agent 工具

**适用场景**：RAG 场景、长文档压缩、学术研究

**结论**：不适合需要缓存命中的生产场景。

---

### 2.5 The Token Company（商业服务）

**它做什么**：云端 ML 网关，训练了 "Bear-2" 模型做 keep/delete 分类。

**对缓存的影响**：
- 助手消息直接透传（不影响缓存）
- 但用户消息和系统消息会被压缩
- 压缩结果取决于模型版本，版本更新时输出会变

**问题**：
- 数据需要发送到云端（隐私问题）
- 商业 SaaS，不是开源
- 模型更新可能导致缓存失效

**结论**：不适合对数据隐私和缓存稳定性有要求的场景。

## 三、核心问题回答：压缩到底会不会降低缓存命中率？

### 3.1 答案取决于"压缩什么"

| 压缩的内容 | 对缓存的影响 | 原因 |
|-----------|------------|------|
| **工具输出**（文件读取、shell 命令、搜索结果） | ✅ 无影响 | 工具输出是每轮的新内容，本来就不在缓存前缀中 |
| **对话历史**（用户消息、AI 回复） | ❌ 降低命中率 | 对话历史是缓存前缀的一部分，改变它就破坏了前缀匹配 |
| **系统提示词** | ❌ 降低命中率 | 系统提示词是最稳定的缓存来源，改变它是最致命的 |
| **工具定义** | ❌ 降低命中率 | 工具定义通常不变，是高价值缓存内容 |

### 3.2 不同工具的策略对比

```
                    缓存安全性
                        ↑
                        │
          lean-ctx      │
          (确定性+       │
           缓存安全)     │
                        │
          RTK           │
          (只压缩工具输出)│
                        │
          Headroom      │
          (无确定性保证)  │
                        │
          LLMLingua     │
          (ML不确定)     │
                        │
          ──────────────┼──────────────→ 压缩率
                        │
```

### 3.3 国内 100 倍差价场景的具体计算

假设：
- 缓存命中：¥0.1/M tokens
- 未命中：¥10/M tokens
- 10 轮对话，系统提示词 + 工具定义 2,000 tokens
- 每轮增量 3,000 tokens（其中 2,000 是工具输出，1,000 是对话）

#### 方案 A：不使用任何工具

```
总 tokens: ~185,000
缓存命中: ~155,000 (84%)
未命中: ~30,000
成本: 155K × 0.1/M + 30K × 10/M = ¥0.315
```

#### 方案 B：使用 RTK（只压缩工具输出）

```
工具输出压缩 80%: 每轮 2,000 → 400 tokens
总 tokens: ~185,000 - (1,600 × 10) = ~169,000
缓存命中: ~155,000 (前缀不变，缓存命中率不变)
未命中: ~14,000
成本: 155K × 0.1/M + 14K × 10/M = ¥0.156
节省: 50.5%
```

#### 方案 C：使用 lean-ctx 工具模式（只压缩工具输出）

与方案 B 类似，但 lean-ctx 还有缓存重读功能（文件重复读取只需 ~13 tokens）：
```
成本: ~¥0.12 - ¥0.14
节省: 55-62%
```

#### 方案 D：使用 Headroom proxy（压缩全部内容）

```
压缩率 80%，总 tokens: ~30,500
但压缩改变了对话历史 → 前缀每轮不同 → 缓存命中率降到 ~10%
缓存命中: ~2,600
未命中: ~27,900
成本: 2.6K × 0.1/M + 27.9K × 10/M = ¥0.279
节省: 11.4%
```

#### 方案 E：使用 lean-ctx proxy（确定性压缩全部内容）

```
压缩率 60%（规则压缩，比 ML 保守），总 tokens: ~74,000
确定性压缩 → 前缀稳定 → 缓存命中率保持 ~84%
缓存命中: ~62,000
未命中: ~12,000
成本: 62K × 0.1/M + 12K × 10/M = ¥0.126
节省: 60%
```

#### 方案 F：RTK + lean-ctx 工具模式（组合使用）

```
工具输出压缩 90% + 缓存重读
对话历史不动 → 缓存命中率 84%
成本: ~¥0.10 - ¥0.12
节省: 62-68%
```

### 3.4 对比总结

| 方案 | 总 tokens | 缓存命中率 | 成本 | 节省 | 风险 |
|------|----------|-----------|------|------|------|
| 不使用工具 | 185K | 84% | ¥0.315 | — | — |
| **RTK** | 169K | 84% | ¥0.156 | **50%** | ✅ 无风险 |
| **lean-ctx 工具模式** | ~150K | 84% | ¥0.13 | **59%** | ✅ 无风险 |
| **Headroom proxy** | 30K | 10% | ¥0.279 | **11%** | ❌ 缓存失效 |
| **lean-ctx proxy** | 74K | 84% | ¥0.126 | **60%** | ⚠️ 需验证确定性 |
| **RTK + lean-ctx** | ~140K | 84% | ¥0.11 | **65%** | ✅ 无风险 |

## 四、为什么"只压缩工具输出"就够了？

### 4.1 上下文窗口里到底装了什么？

每次 API 请求，发给 LLM 的完整内容包括 **所有历史轮次的全部内容**：

```
┌─────────────────────────────────────────────────────────┐
│ 系统提示词 + 工具定义           ← 每轮重复发送，缓存命中  │
├─────────────────────────────────────────────────────────┤
│ 第1轮 用户消息                                          │
│ 第1轮 AI 回复 + 工具调用                                │
│ 第1轮 工具输出（文件内容、shell结果）  ← 很大！不在缓存中 │
│ 第1轮 AI 基于工具输出的回复                              │
├─────────────────────────────────────────────────────────┤
│ 第2轮 用户消息                                          │
│ 第2轮 AI 回复 + 工具调用                                │
│ 第2轮 工具输出（文件内容、shell结果）  ← 很大！不在缓存中 │
│ 第2轮 AI 基于工具输出的回复                              │
├─────────────────────────────────────────────────────────┤
│ ...（每轮都会累积）                                      │
├─────────────────────────────────────────────────────────┤
│ 第N轮 用户消息（当前）                                   │
└─────────────────────────────────────────────────────────┘
```

**关键事实**：第 2 轮的请求中，包含了第 1 轮的 **全部内容**（包括工具输出）。LLM 是无状态的，所以每轮都要重新发送所有历史。

### 4.2 各部分内容占比

一个典型的 30 分钟编程 Agent 会话（Claude Code / Cursor / Codex）：

| 内容类型 | 占比 | 缓存状态 | 举例 |
|---------|------|---------|------|
| 系统提示词 + 工具定义 | ~5-10% | ✅ 缓存命中 | 系统指令、Read/Grep/Bash 工具定义 |
| 用户消息 | ~2-5% | ✅ 缓存命中 | "帮我看看这个文件" |
| AI 回复 | ~10-15% | ✅ 缓存命中 | "我发现第15行有个问题..." |
| **工具输出** | **60-80%** | ❌ **不在缓存中** | 文件内容、grep 结果、git diff、test 输出 |

**工具输出是上下文窗口中体积最大的部分，且每次都是新内容，不会被 Provider 缓存。**

### 4.3 工具输出的典型体积

| 工具调用 | 单次 Token 数 | 一个 session 中的次数 | 总计 |
|---------|-------------|-------------------|------|
| `cat`/`Read` 读文件 | 1,000-5,000 | 20-50 次 | 20K-250K |
| `grep`/`rg` 搜索 | 2,000-10,000 | 5-15 次 | 10K-150K |
| `git diff` | 1,000-5,000 | 5-10 次 | 5K-50K |
| `git status`/`git log` | 500-2,000 | 10-20 次 | 5K-40K |
| `pytest`/`npm test` | 2,000-8,000 | 3-10 次 | 6K-80K |
| `ls`/`tree` | 200-1,000 | 10-30 次 | 2K-30K |
| **总计** | | | **~50K-500K** |

### 4.4 这意味着什么？

```
上下文窗口总 token
├── 系统提示词 + 工具定义 (~5-10%)  ← 缓存命中，压缩反而有害
├── 对话历史 (~15%)                 ← 缓存命中，压缩会破坏缓存
└── 工具输出 (~60-80%)              ← 不在缓存中，压缩是纯收益
                                      ↑
                               RTK 和 lean-ctx 压缩的是这部分
```

**压缩工具输出 = 压缩上下文中最大的那块 + 对缓存零影响 = 纯省钱，无任何副作用。**

### 4.5 具体效果（以 Claude Code 200K 窗口为例）

| 内容 | 压缩前 | 使用 RTK 后 |
|------|--------|------------|
| 系统提示词 + 工具定义 | 3,000 | 3,000（不动） |
| 对话历史（10轮） | 20,000 | 20,000（不动） |
| 工具输出（10轮） | 120,000 | **24,000**（压缩 80%） |
| **总计** | **143,000** | **47,000** |

- Token 减少：**67%**
- 缓存命中率变化：**不变（84%）**
- 成本变化：**减少 50-65%**

这就是为什么 **不需要压缩对话历史**——只压缩工具输出就已经能减少大部分 token 了。

## 五、最终建议

### 5.1 国内 100 倍差价场景的最优策略

```
最优策略 = 只压缩"本来就不在缓存中的内容"
         = 工具输出 + 文件读取 + shell 命令
         = RTK + lean-ctx 工具模式

绝不动的内容 = 系统提示词 + 工具定义 + 对话历史
```

### 5.2 具体推荐

| 你的场景 | 推荐方案 | 理由 |
|---------|---------|------|
| **编程 Agent 日常使用** | RTK | 零风险，50% 节省，单二进制文件 |
| **需要更全面的上下文管理** | RTK + lean-ctx | 65% 节省，零缓存风险 |
| **对话历史很长，想压缩历史** | lean-ctx proxy | 确定性压缩，缓存安全有保证 |
| **Provider 缓存差价 < 10 倍** | Headroom | 缓存损失小，ML 压缩率更高 |
| **Provider 缓存差价 > 50 倍** | 避免 Headroom proxy | 缓存损失可能超过压缩收益 |

### 5.3 使用 Headroom 的注意事项

如果你决定使用 Headroom：
1. **只用工具模式**（`wrap` 或 MCP），不要用 proxy 模式压缩全部内容
2. **配置只压缩工具输出**，不要压缩对话历史
3. **监控缓存命中率**，如果 Provider 有相关指标
4. **避免 ML 压缩器**（Kompress-base），使用规则压缩器

### 5.4 什么时候可以放心使用 Headroom proxy？

- Provider 缓存差价 < 10 倍（如 OpenAI 的 50% 折扣）
- 对话历史很短（< 1000 tokens）
- 你不在意缓存命中率（如使用订阅制）

## 六、工具选择决策树

```
你的 Provider 缓存价格差是多少？
│
├─ > 50 倍（国内大部分 Provider）
│   │
│   ├─ 你主要需要压缩什么？
│   │   │
│   │   ├─ 工具输出（文件、shell、搜索） → RTK + lean-ctx（工具模式）
│   │   │
│   │   └─ 对话历史 → lean-ctx proxy（确定性压缩）
│   │       ⚠️ 不要用 Headroom proxy
│   │
│   └─ 你需要 ML 压缩吗？
│       └─ 不需要 → 规则压缩就够了
│
├─ 10-50 倍
│   │
│   └─ 都可以，但 lean-ctx 更安全
│
└─ < 10 倍（如 OpenAI）
    │
    └─ Headroom proxy 也可以，ML 压缩率更高
```
